# Architecture

## Runtime boundary

The backend is a Java 21 / Spring Boot modular monolith built with Maven. It owns REST APIs, validation, business rules, persistence, uploads, document processing, retrieval, AI-provider calls, and application review orchestration. Neon managed PostgreSQL is the only application database. Docker Compose runs the backend only; it has no local PostgreSQL or Node.js business service.

React + TypeScript is the frontend. Vite and Node.js/npm are used only to build/test/serve the frontend during development. The browser calls the configurable Spring Boot API base URL. CORS allows the configured frontend origin.

## Backend modules

- `loanproduct`, `discovery`: persisted catalogue queries, `BigDecimal` EMI, deterministic matching. Free-text loan-requirement interpretation is still structured-field fallback only.
- `policydocument`: PDF signature/parser validation, generated-key Docker-volume storage, PDFBox page extraction, retry/status handling.
- `policyqa`: page-aware chunking, OpenAI-compatible embedding/chat provider abstractions, pgvector persistence and cosine retrieval, bounded evidence-grounded question answering and abstention.
- `application`, `user`, `audit`: demo customer creation, product-validated application creation, signature-checked uploads, persisted deterministic document/affordability/compliance check results, status history and audit rows. No route approves/rejects.
- `health`, `common`, `config`: database health, API error envelope, validation, CORS, and runtime configuration.

## Policy indexing and RAG

Policy uploads are extracted page by page. Chunking is deterministic, bounded, overlapping, and retains page/document-version metadata. Provider embeddings are dimension/finite-value validated before a transactional replacement of chunks/vectors. Only documents marked `INDEXED` are searchable. Similarity is `1 - cosine_distance`, an ordering signal rather than factual confidence. The response source list is constructed from retrieved persisted records, not generated by the LLM. Empty retrieval abstains. Document text is untrusted prompt data; context is bounded and cannot override policy evidence.

The configured defaults use OpenAI-compatible API endpoints: `text-embedding-3-small` and 1536 dimensions, and `gpt-4o-mini` for chat. A missing `OPENAI_API_KEY` causes a sanitized 503 for AI requests. PDF extraction/page text is retained if vector indexing fails, and the policy document can be retried. These provider calls have not been live-verified in this repository task.

## Application review safety

Creating a customer profile is part of database-backed JWT registration, but identity is not verified. Authentication provides `CUSTOMER` and `REVIEWER` roles: customers create applications/upload documents and view review follow-ups, while reviewers receive the review queue, run deterministic checks, and record human decisions. Review responses persist automated findings, reviewer identity/note/time, and exact requested document types. An application with a selected catalogue product must match its active amount and tenure range. Review checks look for demo document types `IDENTITY`, `ADDRESS`, and `INCOME`; presence is never identity/authenticity verification. Affordability is an EMI estimate from the persisted maximum rate and unverified declared income. KYC, sanctions, bureau, and regulatory integrations are unavailable and are persisted as such. Every review requires a human decision; do not expose this demo publicly.

## Database and migrations

Flyway is disabled by default. Hibernate `ddl-auto=validate` does not create or alter schema. V1–V3 define core tables and policy extraction. V4 adds `INDEXED`, `vector(1536)`, pgvector, and HNSW cosine indexing. V5 adds application-upload checksums and duplicate protection. V4/V5 are generated but not run. Before applying to Neon, inspect the exact target and migration history, confirm pgvector support/availability, review pending SQL, and ensure a recovery point. No destructive/reset operations are used.

## Docker and storage

The backend image has a Maven + Temurin 21 build stage and a Temurin 21 JRE runtime stage running non-root. Neon/provider secrets are injected at runtime. Compose mounts one named volume at `/var/lib/lending` with logically separated `policies/` and `applications/` directories. This local filesystem is for a demo and needs replacement by managed object storage and a backup plan for production.

## API and UI

See [API contracts](api-contracts.md). The React page uses a centralized typed API helper and live requests for catalogue/EMI/recommendations, policy document upload/list/page preview/Q&A, and customer/application/document/review. Loading, empty, and error states are shown. Product data is never hardcoded in live UI paths. Frontend bundles contain no service secrets.
